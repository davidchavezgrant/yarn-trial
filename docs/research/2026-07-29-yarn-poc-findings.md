## Does the grounding/exploration phase help? — measured

Same task, same app, same model; `NO_GROUNDING=1` disables the appmap.

**Task A — change cursor style** (small, one settings page):

| Run | Actions | Wall clock | Model calls | Output tokens |
|---|---|---|---|---|
| **grounded** | 5 | 51s | 6 | 1,695 |
| **ungrounded** | 8 | 88s | 9 | 2,383 |

**Task B — create draft, write a 2-scene script, set voice** (multi-surface):

| Run | Actions | Wall clock | Output tokens |
|---|---|---|---|
| **grounded** | 17 | 236s | 8,463 |
| **ungrounded** | 22 | 295s | 10,378 |
| **grounded + method dictated in the prompt** | **6** | ~73s | ~2,000 |

So on *these* tasks grounding buys roughly **20–40% fewer actions/time/tokens** — real but
modest. **That understates it badly**, because the model already had partial prior knowledge
of both apps' conventions. On a task it genuinely does not know, the gap is **3.25×** — see
"Proving discovery from zero" below.

The third row is **not an autonomy measurement** — it is the cost of the task when the method
is handed over for free. It is retained only because it upper-bounds what recipe compilation
would buy (see below); it must never be quoted as a run result.

### The much bigger lever: recipes

That third row is the finding of the day, and it was an accident — a measurement error that
turned out to quantify something useful. The 6-action run recorded earlier today used this
task text:

> "…write a two-scene script *(use `set_value` on each scene's text block; use the timeline
> 'Add scene' button to create the second scene)*, then set the voice to Cassidy."

I had hand-fed the *method* into the prompt without registering that I'd done so. Removing
that parenthetical — same app, same grounding notes — took the same task from **6 actions to
17**. The appmap tells the agent *where things are*; the recipe tells it *exactly how to do
this task*, and the second is worth ~3× the first.

That is the empirical case for **recipe compilation**: after a task succeeds once, store the
verified action sequence and replay it, calling the model only when a verification step
fails. Grounding makes the first run cheaper; recipes make every subsequent run nearly free.

### On "there's still a lot of thinking during the run"

Correct, and grounding barely dents it, because they're different costs:

- **Grounding removes *navigational* thinking** ("where does this live?").
- **It does not remove *per-action* thinking** — every step still costs a full model call to
  read the observation, choose one action, and write an expectation (18 model calls for 17
  actions above).

The ~10s/action is structural to the observe→decide→verify loop, not to ignorance of the app.
Only recipe replay removes it: a replayed happy path is 0 model calls.

### Caveats on these numbers

- **"Grounded" here = contaminated curated notes** (see correction note at top). The clean
  explore-only grounding condition is being re-measured.
- Single sample per condition; model runs vary a lot (an earlier grounded attempt at Task B
  spent 23 actions failing to rename a draft). With observed within-condition variance that
  large, a single-sample 20–40% delta is suggestive, not established.
- The grounded Task B row has **no surviving run log** (artifact lost to hand-copying; see
  correction note).
- Task B ran against a workspace cluttered with ~6 "Untitled" drafts from prior runs, which
  inflates both conditions equally but makes the absolute numbers pessimistic.
- Grounding's clearest historical win is **dead ends**, not search: on Notion Calendar,
  Settings is a dead end for the timezone control, and ungrounded runs wasted 2 actions there
  every single time. Yarn's surfaces are shallower, so grounding had less to save.

## Prompt hygiene — a measurement error, and the guard against it

Two demo takes were run with the *method* written into the task prompt, not just the goal:
the Yarn script run (`use set_value on each scene's text block…`) and — more consequentially
— the Notion Calendar timezone take that was emailed out, whose prompt dictated the full
sequence (right-click the label, click the search field, select all, type Paris). Both were
reported as clean autonomous runs. They were not: the prompt was doing part of the agent's
job, and nothing in the run log distinguished them from an honest run.

**Re-measured on 2026-07-29 with goal-only prompts** (task text: "Change my primary time
zone to Paris" / "…to New York", nothing more):

| Condition | Actions | Wall clock | Output tokens | Verified |
|---|---|---|---|---|
| grounded, goal-only | **3** | 43s | 786 | 2/3 ✓ (step 1 omitted an expectation) |
| ungrounded, goal-only | **5** | 52s | 1,469 | 5/5 ✓ |

So the capability claim survives the correction intact — the agent finds the timezone control
from a bare goal, and the earlier hinted take was not load-bearing for it. The ungrounded run
spent its two extra actions exactly where the appmap says it would: opening Settings, finding
it a dead end, backing out. That is grounding's real contribution — skipping known dead ends,
not raw search.

**Guard (`auditTaskPrompt`, `src/harness.ts`, tests in `src/harness.test.ts`)**: the agent now
refuses to run when a task prompt names driver/AX internals (`set_value`, `element_index`,
`AX*`) or dictates interaction mechanics (two or more of click/press/keystroke/`cmd+`/select
all). Naming a UI *surface* ("open the Script tab") stays legal — that is task specification.
`--hinted` opts in for filming takes and stamps `hintedPrompt: true` into the run log, so a
dictated run can never again be mistaken for an autonomous one after the fact.

Method knowledge belongs in a grounding file, where it is a declared, budgeted, measurable
input — which is exactly what Jasper's ~24h per-app grounding allowance describes. (Since
this was written, grounding files were split into two tiers to keep that input honest:
`docs/appmaps/` for autonomous exploration output, stamped with a provenance header, and
`docs/recipes/` for hand-curated notes. Correction note 1 above is why — task-specific
recipes had been hand-added to the appmaps that "grounded" runs were measured against.)

## Proving discovery from zero — and what the Notion numbers actually measured

`NO_GROUNDING=1` removes our appmap. It does **not** remove what the model absorbed in
pretraining, so on a well-known app an "ungrounded" run measures *recall*, not discovery.
`src/prior.ts` is the control: it asks the model for the control path with no observation,
no tools, no notes.

**Notion Calendar → KNOWN: partial, CONFIDENCE: medium — and the recalled path is wrong.**
The model routes confidently to Settings ▸ General ▸ Time zone (the actual dead end) and
mentions the real gutter control only as an uncertainty. That is exactly the shape of the
5-action ungrounded run: act on the prior (open Settings), *see* that it is a dead end,
abandon it, pivot to the gutter. So that run measured recovery-from-bad-recall. It is a good
result — screen-reading beat a confident wrong memory — but it is not discovery from zero,
and the 3-vs-5 gap is not a clean discoverability measurement.

**Yarn → KNOWN: no, PATH: UNKNOWN, CONFIDENCE: high (in not knowing).** The model does not
even recognise the term "Pointer-first". That makes Yarn a genuine zero-knowledge target.

**Clean pair, identical home state (Library), goal-only prompts, same task:**

| Condition | Actions | Wall clock | Output tokens | Verified |
|---|---|---|---|---|
| grounded (curated notes — see correction note) | **4** | 36s | 1,074 | 4/4 † |
| **zero-knowledge** (no appmap, no prior) | **13** | 148s | 4,978 | 11/13 † |

† Old lenient grader. The grounded condition also predates the appmap-provenance split, so
its notes were the contaminated curated tier; the zero-knowledge row is clean by construction.

**3.25× on actions, 4.6× on tokens** — and it still succeeded. So yes: discoverability
contributes far more than the earlier 20–40% figure suggested. That figure came from tasks
where the model already half-knew the app; it is a floor for *familiar* targets, not a
measure of grounding's value on a new one.

The zero-knowledge run's 13 actions are also qualitatively interesting: it searched Settings,
scrolled it, backed out, opened the Insert menu, hit the record button (which spawns the
un-driveable recorder window and blanked the AX tree), recovered with Escape, then found
Brand Kit ▸ Screen Clips on its own. Two unverified steps, both from that self-inflicted
recorder detour. It is genuine search, including a real mistake and a real recovery.

### Start-state discipline (added after a near-miss)

A run that starts wherever the previous run stopped inherits that navigation for free. The
grounded Yarn cursor task first reported **3** actions — because the app was already on the
Screen Clip Settings page it ends on. From the home view the same task is **4**. That
one-action difference was about to be written up as a grounding win.

Fixed in the harness: `APP_HOME` declares a home control per app and `resetToHome` clicks it
before every task. Every run log now records `homeReset`, and apps with no declared home log
`"none"` rather than silently skipping. All numbers in this section are post-reset.

## Realistic user phrasing — works, but "show me how" is ambiguous

Every measurement above used an imperative goal ("Change my primary time zone to Paris").
Real requests won't look like that, so both apps were re-run with the phrasing a user would
actually type.

| App | Prompt | Actions | Verified | Interpretation |
|---|---|---|---|---|
| Notion Calendar | "Show me how to change the time zone to New York" | 9 | 8/9 | **Did it** — changed the setting |
| Yarn | "Can you show me how to change the cursor style in my screen recordings?" | 2 | 2/2 | **Demonstrated it** — opened the Cursor Style combobox to reveal the three options and deliberately left the setting unchanged |

Conversational phrasing is not a problem for task completion. But the two runs resolved
"show me how" in opposite directions, and Yarn's run said so explicitly in its summary
("intentionally left unchanged since the user asked to be shown how"). Neither reading is
wrong — the phrasing genuinely admits both.

**For a demo-recording product this needs deciding, not detecting.** A user asking "show me
how to X" almost certainly wants a recording of X happening, not a recording of a menu being
opened. The fix belongs in prompt normalization ahead of the agent (rewrite requests into
imperative goals, or state a standing rule that demos perform the action), not in the model.
Left as an open question because it is a product call.

## The verification hole this uncovered (fixed)

The first user-phrased Notion run reported **"success after 3 actions" with 0/3 steps
verified**. Every act call arrived carrying `expectation: {"description": "(none provided)"}`
and the harness executed it anyway, then reported an unqualified success. The run log was
indistinguishable from an honest pass.

Cause: OpenRouter does not strictly enforce required tool fields (LIMITATIONS §5), so an
omitted expectation arrives silently. The defect clustered entirely on Notion Calendar (4 of
6 steps across runs) and never on Yarn (0 of 20) — plausibly because Notion's appmap contains
a complete verified recipe, so the model emits the known action without reasoning about what
should change.

The harness now **refuses to execute** an act call with no `textIncludes`/`textExcludes`,
returning an error that costs the model a turn and forces a re-issue. The DONE verdict is
qualified (`success CLAIMED — N/M steps UNVERIFIED`) and the log carries `verifiedSteps`,
`unverifiedSteps`, `expectationRejections`.

It paid off on the first gated run: with a real expectation attached, step 4 typed
`New York` into the pre-filled city field without clearing it, the field read `ParisNew York`,
verification failed, and the model recovered (select-all → delete → pick the row). That is a
real bug the previous harness had been reporting as a verified step.

What the honest numbers say:

   grader and machine-checked goal evidence — including 5 ungrounded runs doing genuine
   search. Self-driving on real multi-step tasks stands.
2. **Grounding's honest value is ~2–2.5× on actions and tokens** (4-vs-10 twice on Yarn;

   recipes needed.

   visible pre-action (non-discriminating) — honest "this check proves nothing" labels, not
   false FAILs. The old logs would have called all of them verified.
4. **All appmap grounding is now measurable**: every run log records grounding provenance
   (`explore`/`curated`/`none`) plus the appmap's content hash, so a "grounded" claim can be
   audited after the fact.

## Does grounding buy CORRECTNESS, not just speed? — yes, and it is the bigger finding

Prompted by David asking whether the ~5-minute grounding pass buys anything beyond time.
Re-reading the Yarn cursor A/B step-by-step, the two arms did not do the same thing:

| | Grounded | Ungrounded |
|---|---|---|
| Route | sidebar → Brand Kit → Screen Clips | open a draft → Project actions → Screen Clip Settings… |
| Scope changed | **brand-wide default** | **that one draft's override** |
| Goal check | PASSED | PASSED |

**Verified independent, not two views of one store** (probe, 2026-07-29): wrote `Original`
to the per-draft panel, then read brand level — brand still read `Pointer-first`. Two
separate settings. (The probe's write was reverted.)

So on the task "change the cursor style to Pointer-first", the ungrounded agent changed a
per-draft override on an arbitrary draft while the brand default stayed as it was. Both runs
verify, both summaries are truthful about what they did, and **the harness cannot tell them
apart** — the goal check only asks "does a control named Cursor Style read Pointer-first
somewhere in the final observation", which is true in both scopes.

Implications, in order of importance:

1. **Grounding buys correctness, not merely speed.** The appmap contains "Screen Clips = the
   cursor/motion defaults page" and separately notes that per-draft overrides exist. That
   knowledge is what puts the grounded arm in the right scope. Ungrounded, the agent found
   *a* control matching the words in the task and stopped — reasonable, and wrong.
2. **This is a scope-ambiguity class, not a Yarn quirk.** Any app with global defaults plus
   per-document overrides (editors, IDEs, design tools, browsers) has it. For Yarn's demo
   pipeline it matters concretely: a demo recorded after a per-draft-only change looks right
   in that draft and wrong everywhere else.
3. **Our verification has a blind spot it cannot close alone.** Substring checks over the
   focused window can confirm *a* control reads the target value; they cannot confirm it is
   the *intended* control. Closing it needs either scope-aware evidence (assert the value
   while on the brand page — i.e. grounding again) or a task statement that names the scope.
4. **It reframes the ungrounded numbers.** "10 actions vs 4" is not purely a search-cost
   penalty; ~4 of those ungrounded actions were spent arriving at, and then confirming, the
   wrong scope. Speed and correctness degrade together.

Not yet measured: how often this happens. n=4 ungrounded cursor runs, and all four chose the
per-draft scope — consistent, but one task on one app. The obvious next test is a task with a
known-unambiguous target (only one place it can live) to separate "grounding fixes scope
errors" from "grounding fixes search".

### Follow-up: appmaps are now stored as prose AND a graph

Prose could not express "this control exists at two scopes", so exploration now emits both
`docs/appmaps/<app>.md` (prompt input) and `docs/appmaps/<app>.json` (a node/edge graph for
code). Controls carry a `settingKey` naming the setting independent of where it is edited,
plus a `scope`; two nodes sharing a settingKey across scopes are a detected ambiguity, and
the harness appends an explicit warning to the prompt naming both candidates.

Re-running exploration with this schema found the problem is **much wider than cursor style**:
**14 Screen Clip settings** are dual-scope (brand default vs per-project override) — shadow,
zoom, motion blur, sound effects, cursor scale, and more. The graph even recorded the
evidence unaided: *"Observed Arrow-first while the brand default was Pointer-first - separate
stores."*

Behaviour change verified on the same task that previously failed silently: the agent now
reasons "persist the **brand-wide** cursor style change" and reports "Scope changed: brand
default, not a single project's override." (`out/runs/2026-07-29T20-46-15-yarn.json`,
`…T20-47-33-yarn.json`; both probe changes reverted.)

Caveat: this is one task, before/after, not a controlled A/B — it shows the warning reaches
the model and changes its stated reasoning, not a measured error-rate reduction.

## Does the screenshot earn its place? — vision A/B (canonical task)

`--no-vision` drops the screenshot from the observation; the text block is byte-identical
across arms, so the flag isolates one variable. Canonical prompt ("show me how to change the
cursor type"), Yarn, explore-grounding, home reset verified on every run, arms interleaved so
app-state drift hits both equally.

| Arm | n | Actions | Wall clock | Output tokens | Input tokens/call | Success |
|---|---|---|---|---|---|---|
| vision ON | 3 | 2.0 | 50s | 1,793 | ~16,000 | 3/3 |
| vision OFF | 2 | 1.5 | 45s | 1,842 | ~14,300 | 2/2 |

**The screenshot is not carrying this task.** Every run succeeded with a machine-checked goal
check either way, and the no-vision arm was no slower and used no more actions. The image
costs ~1,700 input tokens per model call (~11%) and buys nothing measurable here.

Why that is plausible rather than surprising: on the AX backend every element already carries
a role, label, value and frame, and *every verification check runs against text*. The
screenshot is redundant with the channel the harness actually grades.

Scope of the claim — deliberately narrow:
- One task, one app, n=2–3. This is a smoke test, not an established result.
- The task is navigational ("show me where"). Nothing here speaks to tasks needing spatial
  reasoning (drag targets, canvas work, "click the red one"), reading rendered text the AX
  tree omits, or diagnosing a visually-broken state.
- AX backend only. The DOM backend's semantic_v2 budget drops nodes, so the screenshot may
  matter more there — untested.

Worth re-testing before turning vision off by default, but the direction is clear enough that
`--no-vision` is a reasonable cost lever for navigational tasks in a throughput pipeline.

### Home reset was silently failing (found by this A/B)

The first attempted pair was void: the vision-OFF run logged `homeReset: failed` and finished
in 1 action because it *started on the settings page the previous run left open*. Cause: the
prior run left the Cursor Style dropdown open, and Yarn's dropdowns overlay the page such
that sidebar elements vanish from the AX tree entirely — so `resetToHome` could not find
"Library" and gave up.

That is the exact non-comparability the reset exists to prevent, and it was only visible in a
field of the run log. Fixed: `resetToHome` now presses escape and retries once when the home
control is missing (3 of the 4 valid runs above needed it), and the agent prints an explicit
NOT-comparable warning when a reset fails.

## "Show me how to X" now performs X

The vision A/B surfaced a product question the harness had been answering inconsistently:
given "show me how to change the cursor type", the agent navigated to the Cursor Style
dropdown, opened it, and described the remaining steps in its summary — truthful, and useless
as a demo video. Nothing in the prompt said which reading was intended, so it varied per run.

Resolved in favour of performing the action, since the artifact is a recorded demo. The
prompt now states that instructional phrasings are requests to do the thing end to end; that
a task naming no value leaves the choice to the agent rather than licensing a stop-short; and
that changes must be committed and confirmed persisted.

**Irreversible actions are the exception** — delete, publish, export, send, share, purchase,
account changes. There the agent goes to the final confirmation step, does not confirm, and
says so. Without this the same instruction would make "show me how to delete a draft" destroy
a draft.

Verified (`out/runs/2026-07-29T21-0*.json`):

| Task | Result |
|---|---|
| show me how to change the cursor type (×2) | 4 actions; picks a value, saves, confirms the Save affordance is gone, stays at brand scope |
| show me how to delete a draft | stops with Project actions open on Delete, never clicks; 12 drafts before, 12 after |

## Harness bugs found (all fixed today)

1. **`set_value` sent `text` where the driver expects `value`** — every direct field write
   silently failed. This is why an early run burned 7 actions deleting a title word-by-word
   with `option+delete`. Fixing it is what made the 6-action (method-dictated) run possible.
2. **`type_text` didn't pass `element_index`** — text went to whatever had focus. In
   Electron a click often doesn't take focus, so keystrokes hit the app's global shortcuts
   (that's where the phantom comment overlay came from). Now targets the element directly.
3. **Unknown action names crashed the run** (`toActionRequest` threw on a model-invented
   `wait`). Now returns a typed error the harness reports back as a rejected step, so the
   model self-corrects. `wait` added as a real action.
4. **Arg parsing dropped the task** when `--backend` was absent (`indexOf` → `-1`, then
   `-1 + 1 === 0` filtered out argument 0). Ran the wrong task against the wrong app.

## Constraints discovered (see LIMITATIONS.md for the full log)

- **Target app must be on the active macOS Space.** Off-Space, Chromium suspends everything:
  0 AX windows, no screenshot, every driver call still reporting success. Programmatic
  activation cannot fix it. Occlusion is fine — only Space-switching kills it.
- **Yarn's screen-clip recorder is un-driveable via AX**: it opens as a separate window with
  no AX children, and while it's open the main window's tree collapses to the menu bar. The
  agent cannot drive the app until it closes. Recording has to be handled outside the AX path.
- **Background clicks are silent no-ops in Yarn** — every click needs
  `delivery_mode: "foreground"`. Stricter than Notion Calendar.
- **The draft title doesn't persist** through the obvious rename paths; one run spent 23
  actions on it. Dropping the rename (plus a method-dictated prompt) got it to 6 actions;
  goal-only, without the rename, it is 17.
- **Driver sessions aren't concurrent-safe** — `Driver.close()` shuts down the shared daemon
  and kills any in-flight run (cost us a 20-action exploration).

## Open questions

- **CDP vs AX** for Electron targets (`src/dom.ts`, in progress): would sidestep AX
  flakiness, the focus/typing problems, and possibly the Space constraint.
- **Recipe replay** — the main lever on per-run cost and determinism.
- How much does grounding help on a *large* app, where search cost is higher? The clean
  re-measure says ~2–2.5× on these two apps; both have shallow surfaces.
- **Should "show me how to X" perform X or demonstrate X?** A product decision (see above);
  the agent currently resolves it per-run and inconsistently.
