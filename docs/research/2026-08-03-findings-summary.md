# Self-driving demo agent — findings

An agent that takes a plain-English task ("show me how to change the cursor type"), performs it
in a real Mac app, and records the result as a demo video.

~200 benchmark runs on Yarn, one model (GPT-5.6 Sol) plus a 9-run Claude Fable comparison, two
tasks (change a setting; write a two-scene script), 142 of them re-graded afterwards by a
separate "judge" model that never saw the agent's own verdict.

**Two ways the agent can drive an app**, and the distinction runs through everything below:

- **CDP** (Chrome DevTools Protocol — the debug channel a browser exposes). Yarn is an Electron
  app, so its interface is a web page underneath, and CDP addresses elements directly by
  identity. Never touches the mouse.
- **AX** (the macOS Accessibility API — the description of on-screen controls that screen readers
  use). Works on any Mac app, including ones with no web layer, but is less precise.

**Grounding** = notes about the app the agent reads before it starts. Four kinds we compared:
nothing at all; an **appmap** (a map of controls and screens, generated by letting an agent
explore for ~40 minutes); **curated notes** (written by a human); and a **procedure** (a short
prose write-up harvested from one earlier run that succeeded).

### Recipes vs procedures — who decides at run time

These are easy to confuse and they are opposites. Both come from one successful run; the
difference is whether a model is involved when you use them.

A **recipe** is machine-executable JSON that *replaces* the model. Replaying one makes no model
calls at all. Each step names an exact control and the text that must appear afterwards:

    click the control named "Project actions" (role: button)
      → then confirm the text "Screen Clip Settings..." is on screen

It is a macro with assertions. Free to re-run, and it produces the identical video every time —
but it cannot adapt. If the control was renamed, or two controls share a name, it stops.

A **procedure** is prose that *informs* the model. Nothing in it is executed; the agent reads it
as notes and still makes its own decisions:

    2. In the current draft's Screen Recording Settings, set Cursor Style to the desired
       option; the verified choice was Pointer-first. This is a per-draft screen clip
       setting, not a brand-wide default.

It is a briefing. It costs a full model-driven run, and it survives the app changing.

Note that last sentence — a caveat about *which* setting was changed. A recipe cannot carry one;
only the tier with a reader can hold advice.

**The measured trade:** recipes went 1/3 with a model on standby to repair broken steps and 0/3
without. Procedures went 3/3 at 848 output tokens, the cheapest grounding we measured.

**Where each belongs:** recipes for re-rendering a demo you have already shot (same customer,
same video, nightly, at no model cost). Procedures for onboarding a new app or task — which is
the expensive problem, and the one they solve.

## What we learned

**Grounding is insurance against a weak actuator, not a general speed-up.** On CDP every level of
grounding passes 3 out of 3 — including giving the agent nothing. On AX, no grounding is 1/3 and
grounding is 3/3. The map isn't making the agent smarter; it's covering for the less precise way
of clicking.

| grounding | success | steps | output tokens (cost proxy) |
|---|---|---|---|
| AX, nothing | 1/3 | 8 | 3671 |
| AX, appmap | 3/3 | 10 | 1418 |
| CDP, nothing | 3/3 | 11 | 1559 |
| CDP, appmap | 3/3 | 9 | 1362 |
| **procedure, harvested from a run that had no map** | **3/3** | **8** | **848** |
| curated human notes | 3/3 | 6 | 817 |

**A short write-up from one successful run beats the 40-minute exploration pass.** Let an agent
work the app out with no map, then have it write down what worked — that write-up matches
hand-written human notes, at 40% less cost than the generated map it would replace, and
identically across three runs. Onboarding a new app may cost a handful of good runs plus a
write-up, rather than a 40-minute automated sweep per app.

**When the agent only sees screenshots, it can't aim.** We gave one group the list of on-screen
elements and another only pictures, on the same driving method where a screenshot pixel and a
click land in exactly the same place. Pictures-only missed its intended target **75%** of the
time; with the element list, **11%**. This is the model failing to localise from an image — not a
bug in our click code, which we confirmed separately.

**Recording the demo was costing a 4x reliability drop, for no benefit.** Filmed AX runs
succeeded 2 out of 13; unfilmed, 26 of 39. Both causes were ours: the window gets resized when
recording starts and we read its layout before it had finished moving; and recording swapped our
reliable "activate this element" click for a coordinate click, on the theory that it moves the
mouse for the camera — which our own recorded data shows it doesn't. Fixed: **2/13 → 6/9**, now
equal to unfilmed.

**A 43-pixel misalignment we'd chased for three days was not a coordinate bug.** The maths was
right the whole time. The same button reported two different positions one moment apart: we were
photographing the app before it finished laying itself out.

**The agent's own report of success is trustworthy on this app** — the independent judge
disagreed on only 4 of 142 runs.

**Our automatic checking works on product demos and goes blank on open-ended requests.**

| | "change a setting" | "write a two-scene script" |
|---|---|---|
| judge: pass / fail / can't tell | 31 / 2 / 0 | 13 / 17 / 12 |
| could the judge verify from the video | 30 of 33 | 8 of 42 |
| steps producing no checkable evidence | 32% | 71% |

Product-use demos — what Yarn ships — grade cleanly. "Write me something good" does not, because
there's no fact to check against.

**Only human-written notes made the agent change the *global* setting.** Yarn has settings in two
places: a brand-wide default and a per-document override. Every automatically-generated form of
grounding sent the agent to the per-document one; only human notes sent it to the brand default,
5 times out of 5. The generated map contains **both** routes, so this is about which one reads as
the obvious choice — worth fixing before a customer's demo edits one draft instead of their
defaults.

**Claude Fable performed comparably** to Sol on the same cells: 6/9, no disagreements with the
judge.

## What we didn't learn

- **Whether a map built from screenshots alone is useful.** That run went out without its map and
  was automatically disqualified. I reported it as a result first and had to retract it.
- **Whether any of this transfers to a second app.** We measured a second *task*, never a second
  application.
- **Whether "recipes" work.** A recipe is a frozen click-by-click replay of a successful run.
  It succeeded 1/3 with a model on standby to fix broken steps, 0/3 without. Two causes found and
  fixed; not yet re-measured.
- **Whether nudging the agent's click onto the nearest real control rescues the
  screenshots-only mode.** Built, not yet run.
- **Whether the script-writing runs would finish with more steps.** Three hit a step limit while
  still making progress. Limit removed, re-runs outstanding.

## What to build

1. **CDP as the primary way of driving.** Zero coordinate errors, most precise, and unaffected by
   recording. AX is the fallback for apps with no web layer.
2. **Procedure harvesting** — have successful runs write down what worked. Cheapest grounding we
   measured, and the only one that removes the per-app exploration pass entirely.
3. **Say which setting was changed, in the demo itself.** "This changed one draft, not your
   defaults." Small step from what the agent already reports.
4. **Run the click-nudging experiment.** Already built; it decides whether the much larger
   image-analysis version is worth anything.

## What not to build

1. **Screenshots-only as a shipping mode.** The limit is the model's eyesight, and no improvement
   to our clicking moves it.
2. **Recipes, until they handle variation.** A frozen sequence breaks on two buttons with the same
   name, or on re-typing a value it typed last time. And a task whose steps leave no checkable
   trace — most creative work — can never be frozen at all.
3. **Image-analysis click correction.** The real fix for apps with no element list, and a big
   build. Wait for the nudging experiment.
4. **Any more work on the coordinate maths.** It was never wrong.

## Reading the dashboard

Two discovery columns are unreliable: `seen` and `surfaces`. One exploration pass logged 6609
controls seen against an identical run's 293 — purely because it scrolled a long list. Both
produced comparable maps. Use **graph nodes** (how much of the app was mapped) and **actuated**
(how many controls were actually operated).
