*Self-driving demo agent — what ~200 benchmark runs said*

Context: an agent takes a plain-English task ("show me how to change the cursor type"), performs it in Yarn, and records a demo video. ~200 runs, two tasks, 142 of them re-graded afterwards by a separate "judge" model that never saw the agent's own verdict. Full write-up in `docs/research/2026-08-03-findings-summary.md`.

Two bits of vocabulary, because everything below turns on them:
• *CDP* (Chrome DevTools Protocol — the debug channel a browser exposes). Yarn is an Electron app, so underneath it's a web page; this lets us address controls by identity and never touch the mouse.
• *AX* (macOS Accessibility API — the on-screen description screen readers use). Works on any Mac app, including ones with no web layer, but it's less precise.
• *Grounding* = notes the agent reads before starting. Either nothing, a map generated by letting an agent explore for ~40 min, notes a human wrote, or a short write-up harvested from an earlier successful run.

*What we learned*

• *Grounding is insurance against a weak actuator, not a speed-up.* On CDP every level of grounding passes 3/3 — including giving the agent nothing at all. On AX, nothing is 1/3 and a map is 3/3. The map isn't making the agent smarter; it's covering for the less precise way of clicking.

• *A short write-up from one successful run beats the 40-minute exploration pass.* Let an agent work the app out with no map, then have it write down what worked: 3/3, at 40% less cost than the generated map it replaces, identical across three runs. Onboarding a new app may cost a few good runs plus a write-up instead of an automated sweep per app.

• *When the agent only sees screenshots, it can't aim.* Same driving method, same coordinate space — pictures-only missed its intended target 75% of the time; with a list of on-screen elements, 11%. That's the model failing to localise from an image, not our click code (confirmed separately).

• *Recording the demo was costing a 4x reliability drop for no benefit.* Filmed runs on the AX path succeeded 2/13 vs 26/39 unfilmed. Both causes were ours — we photographed the window before it finished resizing, and recording had swapped a reliable click for a less reliable one on a theory our own data disproves. Fixed: 2/13 → 6/9, now equal to unfilmed.

• *Our automatic checking works on product demos and goes blank on open-ended requests.* "Change a setting": judge passed 31, failed 2, couldn't tell 0. "Write a two-scene script": 13 / 17 / 12, with 71% of steps leaving nothing checkable. What Yarn ships grades cleanly; "write me something good" doesn't, because there's no fact to check against.

• *The agent's own success report is trustworthy here* — the independent judge disagreed on 4 of 142 runs.

• *Only human-written notes made the agent change the global setting.* Yarn keeps some settings in two places — a brand-wide default and a per-document override. Every auto-generated form of grounding sent the agent to the per-document one; only human notes went brand-wide, 5/5. The generated map contains both routes, so it's about which reads as the obvious choice — worth fixing before a customer's demo edits one draft instead of their defaults.

*What we didn't learn*

• Whether any of this transfers to a *second app* — we varied the task, never the application.
• Whether "recipes" (a frozen click-by-click replay of a successful run) work: 1/3 with a model on standby to fix broken steps, 0/3 without. Two causes found and fixed, not yet re-measured.
• Whether a map built from screenshots alone is useful — that run went out without its map and was auto-disqualified. I reported it as a result first and had to retract.

*What to build*

1. CDP as the primary way of driving; AX as fallback for apps with no web layer.
2. Procedure harvesting — successful runs write down what worked. Cheapest grounding measured, and the only one that removes the per-app exploration pass.
3. Say which setting was changed, in the demo itself: "this changed one draft, not your defaults."

*What not to build*

1. Screenshots-only as a shipping mode — the limit is the model's eyesight, and better clicking doesn't move it.
2. Recipes until they handle variation — a frozen sequence breaks on two buttons with the same name, and a task that leaves no checkable trace can never be frozen at all.
3. Image-analysis click correction — the real fix for apps with no element list, but a big build; we have a cheaper experiment queued that says whether it's worth it.

One caveat for anyone opening the dashboard: the `seen` and `surfaces` columns are unreliable — one run logged 6609 controls against an identical run's 293, purely from scrolling a long list. Use *graph nodes* (how much got mapped) and *actuated* (how many controls were actually operated).
